# 0052-DEF — Step 2 controlled replacement guide (23 November 2026)

The Python and Java utilities are feature-specific and belong only under `tools/`. **No production changes are performed by the default invocation.** They use an existing Windows Cygwin Python 3.10+ and a Java 17+ JDK, SSH to `pluto`, local Docker and the mapped NAS P: drive.

1. Apply this ZIP at the **Windows Diaries repository root** using Beyond Compare 4. Do not overwrite working files outside 0052. Inspect Git branch/revision/status and pinned submodules recorded in the tool's private run evidence.
2. Run offline regression first: `python3 "change-control/in-progress/0052-DEF - correct catalogue image content errors/tests/test_step2_0052.py"`.
3. Generate and validate the JPEG while checking both live catalogue/Files pairs **without writing to NAS or database**:
   `python3 "change-control/in-progress/0052-DEF - correct catalogue image content errors/tools/step2-correct-catalogue-images.py" --mode both`
   This creates the JPEG and preflight evidence under `evidence/Step 2/private/<UTC>/`. Inspect the JPEG visually at full zoom: Whitley Park labels must be readable and geography correct.
4. **For the controlled write window:** Stop the local development Java responder in its IDE first (the script detects a listener on TCP 8081 and refuses to apply while it is running). Run the same Python command with `--mode both --apply` to update the corrected metadata-source JPEG, previously absent processed JPEG, development/prod served Files images and Image 3/18 database metadata. The script copies backups to its private evidence dir before writing, enforces old metadata/checksum/version guards, briefly stops/restarts the production `diaries-responder` Docker container, and attempts rollback on failure. It does not change Fragments, Marquees or unrelated Image IDs.
5. Restart the local development responder using the established IDE startup. Responder startup reconciliation compares database retained projections with MQTT `diaries/images/3` and `/18` and republishes changed entries. Inspect both environment logs and read back retained MQTT metadata; **do not infer success merely from restarting**.
6. Check HTTP image SHA-256 matches the new hashes, the catalogue rows now have version 1 and dimensions 776 × 502 (Image 3) and 720 × 480 (Image 18), protected Image 21/25 content hashes are unchanged, and all before/after Fragment and Marquee references are unchanged. Verify actual Editor/public Reader visual appearance for legacy and IMAGE Fragments. Record the owner acceptance separately; leave Step 2 OPEN until all criteria hold.

**Scope / safety:** The Python script only writes when passed `--apply`; it does not manipulate Btrfs recovery snapshots, backups or unrelated files. Private evidence contains file backups and database row JSON; retain it until acceptance. In the event of a failure, inspect rollback diagnostics before retrying. If it cannot restore the previous state automatically, do not continue or rerun; follow the saved `rollback-file-manifest.json`, `before-catalogue.json` and `rollback-sql.json` and diagnose the exact inconsistent state.

**Known limit:** The tool relies on the source-bundle interface and the 23 November live inventory. It cannot itself perform the final browser visual acceptance or authenticated MQTT retained-topic readback. No claim of completed deployment/closure is implied by including the script.
