The second normal development-tree invocation successfully:

It then exposed two test-fixture defects rather than production-code defects.

## 1. Image-reference URL test consumed the pre-config view model

`ImageFragmentReferenceComponent` deliberately begins its asynchronous runtime-config stream with `null` so retained Image metadata can render before `assets/config.json` has resolved. The spec waited only for `viewModel.image`, which is already present in that initial emission, and therefore asserted the URL while `imageUrl` was still `null`.

Correction: the test now waits for a non-null `viewModel.imageUrl`. No production behavior changed.

## 2. "Image reference already current" fixture dropped the retained lock

The production mutation path requires a post-lock retained Fragment carrying a non-null/new `lock.lockTimeStamp` before it performs or skips the update. The spec replaced the harness's retained Fragment with `{ ...imageFragment, imageId: 202, version: 8 }`, inadvertently removing the harness's lock object. The production code therefore correctly waited for the required locked retained state and timed out after five seconds.

Correction: the test now derives the already-current retained object from `h.liveFragment$.value`, preserving the existing lock metadata while changing `imageId` to 202. No production behavior changed.

The later Karma disconnect / Node `ERR_INVALID_STATE` followed the asynchronous timeout and is treated as secondary test-run fallout, not a separate product defect.
