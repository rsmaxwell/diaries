### Step 12.3 — Automatically retry interrupted receive at the next scheduled invocation (CLOSED 8 November 2026)

**Accepted requirement:** A temporary network failure, receiver outage or interrupted `btrfs receive` should normally self-recover on the **next scheduled run**. Repeated failures remain visible in normal logs and can be corrected manually. The operator accepts a simpler, less elaborate fail-safe boundary.

- Under the receiver's local non-blocking lock, check the exact expected candidate. If absent, send normally. If a valid completed read-only received subvolume exists with matching Received UUID, reconcile rather than resend.
- If a previously interrupted receive left a **clearly incomplete** subvolume with the exact candidate name in the dedicated receiver tree, ensure it is not a protected parent, accepted received snapshot, historical hold or symlink; use fresh Btrfs inspection. Delete only that one candidate with `btrfs subvolume delete`, confirm absence, then retry **once per scheduled invocation**. No recursive filesystem deletion. If evidence is incomplete or the lock cannot be acquired, log and back off without deleting.
- Do not build a per-transfer transaction journal, staged-name stream rewriter, systemd scope, multi-party locking or single-use retry token. Use small agreed-parent files and normal timestamped journal/systemd logs. A second or later failed scheduled run must remain diagnosable; the operator will intervene for persistent errors.
- Compact verification suite: ordinary cycle; interrupted disposable real-Btrfs receive → next-invocation cleanup → successful retransmission; complete receive with lost acknowledgement → no retransmission; two consecutive failures leave agreed parent unchanged; concurrent receiver prune/receive backs off; ambiguous or protected candidate cannot be deleted.
- **Gate:** accepted controlled disposable real-Btrfs test and source regression evidence, without modifying any established production backup. Historical tests for the rejected staged architecture may be archived and removed from Playbooks via the guarded feature tool after reviewing the cleanup manifest; retain essential native/retention regression coverage.
